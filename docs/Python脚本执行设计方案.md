# Python 脚本执行设计方案

状态：设计草案，未实施。本文不代表已有执行能力，也不修改当前 AGENTS.md 中“系统不执行 Skill 代码或脚本”的边界。

## 1. 背景与目标

部署环境没有 Docker。希望 Agent 能执行 Python 完成数据清洗、统计和计算，并为后续执行管理员上传的技能脚本预留清晰边界。

本期仅落地设计文档，不新增代码、依赖、配置或外部服务账号。

目标：

- 应用服务器无需 Docker，不在 API/worker 宿主直接执行模型生成的代码。
- Python 执行通过统一工具接入，继续复用 runtime 工具循环与执行过程展示。
- 执行归属于用户和 Run，支持取消、资源限制、结果截断和审计。
- 执行供应商可替换，领域核心不依赖供应商 SDK。

## 2. 执行方式选择

首选方向：通过 API 调用独立的远程 Python 沙箱服务。E2B 等托管服务作为候选，不在本草案中锁定供应商或承诺其具体 API、隔离与网络能力。

| 方式 | 应用服务器要求 | 适用条件 | 本方案定位 |
|---|---|---|---|
| 托管远程沙箱 | 可访问供应商 API | 数据允许进入该服务，费用和区域可接受 | 优先评估 |
| 内网独立沙箱服务 | 可访问内网执行端点 | 数据不能出内网，有独立执行基础设施 | 同一执行接口的替代实现 |
| Pyodide / WebAssembly | 对应运行环境及进程资源管理 | 依赖包兼容，主要做离线计算 | 后续备选 |
| 宿主 subprocess / exec | 本机 Python | 缺少可靠隔离 | 不采用 |

“没有 Docker”只描述应用部署环境，不限制独立沙箱服务内部使用何种隔离技术。普通容器也不能视为绝对安全边界；实现前需核实供应商隔离、资源上限、取消和数据保留机制。

待部署决策：外网连通性、数据出域许可、服务区域、预算与供应商。这些未确认前保持功能关闭，不发送真实业务数据。

## 3. 首版范围

支持模型调用 `run_python(code, inputs)`，在一次性 Python 沙箱中执行代码，返回结构化状态、受限 stdout/stderr 和 JSON 结果。

首版不支持：

- 任意 Shell 命令、运行时 pip install、模型指定镜像或执行端点。
- 跨调用保留 Python 内存状态或共享可写工作目录。
- 将应用密钥、数据库连接串、宿主目录或用户任意路径传入沙箱。
- 直接执行上传的 ZIP、脚本目录或 SKILL.md 中的代码块。
- 图片、文件产物下载和持久化；这需要独立的文件归属、配额与鉴权设计。

Python 及预装依赖版本由管理员选择的固定环境模板决定。初始候选依赖为 pandas、numpy；只有纳入测试的模板才允许使用。

## 4. 模块与依赖

建议目录（均为待新增或待调整）：

```text
src/
  sandbox/
    types.py           # 不可变执行请求、结果与执行器协议
    remote.py          # 首个供应商适配器：创建、上传输入、执行、取消、销毁
  tools/
    python.py          # run_python 工具定义及参数校验
  services/
    execution.py       # 用户/Run 校验、配额、执行记录、结果归属
  storage/
    repositories/
      executions.py    # 执行记录读写，不自行开启事务
  worker.py            # 装配执行器与每次 Run 的工具闭包
  domains/data/
    tools.py           # 合并注入的工具定义
```

依赖关系：worker 装配 service、executor 与工具；service 持有执行器协议；供应商 SDK 仅在 sandbox 适配器内使用。runtime 继续只处理 ToolRegistry，不知道远程服务、数据库、用户或 Settings。

工具闭包由服务端绑定 user_id、run_id、owner 和 generation。模型参数中不提供这些字段，避免由模型指定执行身份。

## 5. 工具与执行器契约

模型可见输入示例：

```json
{
  "code": "values = inputs['values']\nresult = {'mean': sum(values) / len(values)}",
  "inputs": {"values": [12, 45, 78]}
}
```

`inputs` 必须是有大小与深度上限的 JSON 数据，通过数据文件加载为 Python 变量；不得把未转义的输入拼接进脚本。`result` 是约定的可选 JSON 输出变量，输出协议使用单独结果文件，避免与 stdout 混淆。

应用侧执行器协议应覆盖：

- execute(request, cancellation)：执行并返回标准结果。
- cancel(execution_id)：请求终止，并核实远程状态。
- cleanup(execution_id)：释放远程资源；幂等。

具体同步/异步 SDK 桥接方案在选定供应商后验证，不能让阻塞调用进入 API 的事件循环。worker 现有同步工具链可保留同步执行器接口。

模型可见结果示例：

```json
{
  "execution_id": "服务端生成的执行标识",
  "status": "succeeded",
  "stdout": "",
  "stderr": "",
  "result": {"mean": 45},
  "exit_code": 0,
  "duration_ms": 230,
  "truncated": false
}
```

统一状态：queued、running、succeeded、failed、cancelled、timed_out、unknown。供应商错误映射为稳定错误码，不直接返回供应商异常、凭证或堆栈；Python 用户脚本错误可以返回经过脱敏和长度限制的诊断片段。

## 6. 执行流程与生命周期

1. runtime 选择 run_python，现有工具事件显示代码执行请求。
2. 服务检查功能开关、授权、输入大小、用户配额和 Run fencing，先记录执行意图。
3. 创建一次性沙箱；配置固定环境、资源上限及网络策略。
4. 仅上传本次执行的代码和输入，启动 Python。
5. worker 心跳继续运行；服务监测取消、租约失效、执行截止时间。
6. 接收受限输出，校验结果格式，使用 fencing 更新执行记录。
7. 在 finally 路径尝试销毁沙箱，保存清理状态；后台补偿清理未释放资源。
8. 将结果交回 ToolRegistry，模型据此生成最终回答，或显式发起新的修正执行。

每次调用创建独立沙箱，默认不保留状态。平台支持的远程 TTL 必须设置，作为 worker 崩溃后的兜底，但不能替代主动清理。

应用侧超时不等于远程进程已停止。若无法确认取消或提交是否成功，标记 unknown，继续尝试查询与清理，不自动重放代码。传输重试只用于可证明幂等的请求；执行提交依赖供应商幂等键或明确状态查询能力。

## 7. 隔离、数据和资源策略

- 沙箱执行网络默认关闭；若候选供应商无法可靠禁用或约束网络，不能按本方案上线。
- 不挂载宿主目录、不透传宿主环境变量、不向执行进程注入供应商控制面密钥。
- 不复用不同用户的沙箱、临时文件或可写工作目录。
- 资源限制必须由执行平台强制实施；Python 代码检查或 import 黑名单不是隔离边界。
- MCP/API 在应用侧取数，服务检查归属和数据使用策略后，只向沙箱传入必要数据。凭证留在取数端。
- 工具结果仍是不可信输入，不得被当作系统指令。

建议初始预算（待供应商能力与压力测试确认）：

| 项目 | 建议值 | 执行位置 |
|---|---:|---|
| 代码 UTF-8 大小 | 32 KiB | 工具入口 |
| JSON 输入大小 | 256 KiB | 工具入口；同时受模型上下文预算约束 |
| 单次代码运行时间 | 30 秒 | 远程执行平台 |
| 创建到清理总截止时间 | 90 秒 | 应用执行服务 |
| 内存 | 512 MiB | 远程执行平台 |
| CPU / 进程数 | 1 vCPU / 64 | 远程执行平台，须验证支持 |
| 每用户并发 | 1 | 数据库原子配额 |
| 全局并发 | 4 | 跨 worker 配额 |
| 每 Run Python 调用数 | 5 | 执行服务 |
| 模型可见结果 | 序列化后不超过现有 36000 字节 | 适配器及 ToolRegistry |

输出需要在接收过程中限额，不能先无限缓存再截断。stdout、stderr 和 result 共用结果预算，并保留状态与截断标记。日志只记录标识、状态、耗时、字节数和错误码，不记录完整代码、输入或凭证。

远程计费需同时设置单次生命周期限制、用户配额和每日费用预算；费用未知时先按执行时长与次数限流，不能声称已经实现精确成本控制。

## 8. 持久化、迁移与可观测性

新增 python_executions 表，建议字段：

- id、user_id、run_id、tool_call_id、owner、generation。
- status、provider、environment_version、remote_execution_id。
- code_hash、input_bytes、output_bytes、truncated、error_code、exit_code。
- created_at、started_at、finished_at、deadline、cleanup_status。

远程执行标识仅供服务端运维使用，不直接暴露给模型或其他用户。首版不额外存储完整输入或脚本副本；如果现有 run_steps 保存工具参数，应同步制定执行记录的访问权限、脱敏和保留期限，避免通过时间线复制敏感数据。

表结构使用 SQLAlchemy Core，SQLite / PostgreSQL 一致；时间字段采用 epoch 秒。正式实现需要版本化的增量迁移与旧库升级测试，不能仅写版本标记宣称完成升级。

现有 run_steps 继续展示“调用参数 → 执行结果 → 最终回答”。新增执行表用于追踪外部任务生命周期和补偿清理，不用 run_steps 代替状态机。

运维指标：执行成功率、排队时间、创建时间、运行耗时、超时数、unknown 数、清理失败数、并发数与费用估算。

## 9. Skill 附带脚本的后续扩展

当前上传入口只接收 SKILL.md 文本，不代表安装了 scripts/ 资源。首版 run_python 完成后，再单独扩展技能包管理：

1. 管理员上传带清单的技能包，校验文件数量、体积、文件类型及路径；拒绝符号链接与路径穿越。
2. 清单明确脚本入口、依赖模板和参数 schema，禁止入口指向任意宿主路径。
3. 保存脚本内容哈希与版本；Run 绑定具体版本，执行时校验一致性。
4. 提供 run_skill_script(skill_name, script_name, arguments) 工具，服务端解析批准的脚本。
5. 脚本同样进入独立沙箱；管理员来源不等于免隔离，不开放任意 Shell。

技能脚本若需要内网 API：优先把取数封装为 MCP/受控 API 工具，Python 只做计算。若必须由脚本联网，需另行设计内网执行服务、目的地址白名单和短期最小权限凭证，不隐式放开沙箱网络。

## 11. 分阶段实施与验收

### 阶段 A：供应商验证

确认联网、数据出域、服务区域、密钥管理、隔离机制、网络控制、资源限制、TTL、取消、输出上限、幂等性和费用。用非敏感样本验证真实 SDK 生命周期，再确定依赖版本。

### 阶段 B：执行器与状态机

先写契约测试，再实现协议、单个供应商适配器、状态记录、配额、fencing、取消与清理补偿；保持 runtime 领域无关。

### 阶段 C：工具与展示

注册 run_python，接入现有过程事件；明确 stdout/stderr/result 展示、截断提示及失败状态。更新 AGENTS.md 边界，但只在实际执行能力与隔离验证完成后更新。

### 阶段 D：测试与试运行

- 单元：参数限制、UTF-8 字节预算、结果格式、错误映射、超时及清理失败。
- 集成：多用户隔离、跨 worker 配额、旧 worker fencing、提交结果未知、不重复执行、旧库迁移。
- 真实沙箱（显式开启）：正常统计、无限循环、大量输出、内存超限、禁网、取消、TTL 和资源释放。
- 前端 E2E：执行过程位于最终回答之前、折叠查看、超时可见、取消后状态稳定。
- 保留默认无外网测试路径，真实服务验证单独运行并记录结果，不能用 fake 通过替代真实隔离验证。

上线前必须满足：用户身份不可由模型指定；远程任务能够终止和清理；输出不会无限占用 worker 内存；租约失效不允许旧任务覆盖状态；无网络/资源限制经过真实验证；数据使用与费用策略已确认。
